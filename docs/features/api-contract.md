# API contract (consumer side)

The ui and the photos-api agree on one OpenAPI 3.1 spec. The photos-api repo, [ethannet-media](https://github.com/Ethan-S-Evans/ethannet-media), owns it at `openapi/photos-api.yaml` and generates its Java controller interfaces from it. This repo keeps a **vendored copy**, pinned to a photos-api release, and generates TypeScript types from that copy. The plan this was built from is [2026-11-12-spring-boot-photos-api](../plans/2026-11-12-spring-boot-photos-api.md). See [Architecture](../architecture.md) for how the two repos fit together.

## Files

| File | What it holds |
| --- | --- |
| `packages/schema/openapi/photos-api.yaml` | The vendored spec. Never edit it by hand; change it in the photos-api repo and sync. |
| `packages/schema/package.json` → `photosApi` | Where the spec comes from: `repo`, `path`, and the pinned `ref` (a release tag such as `v0.1.0`, or `null` before the first release). |
| `packages/schema/src/generated/photos-api.ts` | Types generated by `openapi-typescript`. Committed, because the ui imports packages from source with no build step. Never edit it. |
| `packages/schema/src/index.ts` | Friendly names for the generated types, such as `HelloResponse`. Consumers import only from here. |
| `packages/schema/scripts/` | `sync-api.mjs`, `check-api.mjs`, `check-api-upstream.mjs`, and `photos-api-source.mjs` (the tested helpers they share). |

## Using a contract type

```ts
import type { HelloResponse } from "@ethannet/schema";
```

Always `import type`. To expose a new schema, add an alias with a doc comment to `src/index.ts`:

```ts
export type PhotoSummary = components["schemas"]["PhotoSummary"];
```

## Workflows

**Update to a new photos-api release:**

```
pnpm --filter @ethannet/schema sync:api v0.2.0
```

This fetches the spec at that tag from GitHub, writes it to `openapi/photos-api.yaml`, pins the tag in `package.json` and regenerates the types. Then run `pnpm typecheck`: any ui code that no longer matches the contract fails there. Fix it, and commit the sync and the fixes together with a changeset.

**Check for drift:**

- `pnpm check:api` (also part of `pnpm lint`, offline): fails if the generated types don't match the vendored spec. Fix with `pnpm --filter @ethannet/schema generate:api`.
- `pnpm --filter @ethannet/schema check:api:upstream` (needs network): fails if the vendored spec differs from the spec at the pinned ref. Fix with `sync:api <ref>`. Before the first photos-api release, no ref is pinned and it says so.

## Rules

- The photos-api changes the contract first. The ui only ever moves to a released (tagged) version.
- A breaking change in the photos-api spec is a major photos-api release (minor while it's pre-1.0). When the ui adopts it, pick the ui's own bump by its user-facing effect.
- During local development against an unreleased api change, you may run `sync:api <branch-or-commit>`, but pin a tag again before merging.

## Testing

- `pnpm --filter @ethannet/schema test` covers the URL and pin helpers (`photos-api-source.test.mjs`).
- `pnpm typecheck` checks every consumer against the generated types.
- `pnpm test:e2e` proves the ui and a running photos-api agree at runtime (`tests/home.spec.ts` renders the hello response).
